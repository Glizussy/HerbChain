# HerbChain changes — 2 October 2026

This document summarizes the accumulated changes since commit `53d02a8` (plant classification integration). The project now includes a mobile collection flow, a permissioned Fabric supply-chain backend, participant web portals, and optional infrastructure for handling many batches. The scaling features are implemented locally; this does not mean they have been activated or accepted in production.

## 1. Farmer Android app

- Supabase sign-in and account-scoped access replace anonymous submission.
- A guided harvest form captures plant details, location, quantity, photos and collection evidence.
- The existing plant classifier provides a prediction; it does not independently certify safety or approve a harvest.
- The app submits evidence to the backend, which hashes it and records the harvest through Fabric.
- Successful submission shows the batch and transaction IDs. Independent review is required.
- My Harvests and a durable submission outbox support tracking and retry without silently creating duplicate harvests.

Main files: `App.js`, `src/screens/FarmerCollectionForm.js`, `FarmerBatchesScreen.js`, `SignInScreen.js`, and `src/services/{herbBatchService,fabricService,harvestOutbox,plantClassifier}.js`.

## 2. Fabric contracts and enrollment

`blockchain/chaincode/lib/batches.js` implements collection, independent review, proposed/accepted/cancelled custody transfers, laboratory results, processing, packaging, delivery, recall and provenance reads. The contract checks enrolled roles and state transitions. Quantities use whole grams. Transactions record actor identity, transaction ID and ledger timestamp.

`blockchain/chaincode/lib/lineage.js` adds lot splitting and merging, balanced input/output quantities, consumed sources, parent/child provenance and recalled-ancestor checks. New child lots do not automatically inherit a passing laboratory result. These functions require a chaincode upgrade before activation.

`blockchain/enroll-pilot.sh` enrolls role-bearing pilot identities. Private signing keys remain on the backend and are excluded from Git. The existing two-organization Fabric test network is a development network, not a production deployment.

## 3. Backend and participant portals

`server/src/server.js` provides authenticated APIs and serves the participant pages. `gateway.js` connects server-held identities to Fabric using TLS. Authorization is enforced on the backend, not just by hiding buttons.

The web UI includes a dashboard, independent review, custody handoffs, laboratory and processing operations, activity tracking, lot management, labels and public tracing. The dashboard uses simpler wording, responsive layouts, search, filters and pagination. Public tracing intentionally exposes a limited record rather than private photographs, precise locations or internal reports.

The supported participant roles are collector, verifier, aggregator, laboratory, processor, manufacturer, distributor and regulator, with a separate public reader identity.

## 4. Scaling work

| Area | Implemented behavior | Activation needed |
| --- | --- | --- |
| Memberships | Multiple users and organizations, assignments and suspension checks | Database migrations, identity mapping and seeds |
| Batch index | Valid Fabric block replay, scoped lists/search, pagination and atomic checkpoints | Run indexer and verify backfill |
| Evidence | Private immutable archive, hashes and authorized cloud reads | Private storage configuration and verified backfill |
| Transaction queue | Idempotent requests, worker leases, commit reconciliation and explicit rejected-request retry | Database migrations, worker and validation |
| Lots | Split/merge with mass balance, lineage and ancestor-recall holds | Chaincode upgrade and feature flag |
| Bulk handoffs | Up to 20 individually authorized handoffs with per-batch results | Participant configuration and scenario testing |
| Operations | Container/HTTPS templates and queue/certificate checks | Staging deployment and real acceptance testing |

The nine SQL migrations in `server/migrations/` define memberships, indexing, private storage, queued jobs, reconciliation, lot support, metrics and audited retry. They are supplied as source files; this change does not apply them to your live Supabase project.

Queue safety favors investigation over duplicate writes: an uncertain transaction is not blindly resubmitted. A crash after saving a transaction ID but before transmission can require operator investigation. Merges rely on Fabric conflict validation for secondary inputs. Connection caching and lineage traversal are bounded; they are not unlimited scaling.

## 5. Reusable operational scripts

The following helpers are now in `scripts/` rather than only in the original local workspace:

- `start-farmer-api.cjs`: launch the local participant API using enrolled identities and account mappings.
- `start-transaction-worker.cjs`: start the optional transaction worker.
- `start-batch-indexer.cjs`: start the optional ledger indexer.
- `prepare-membership-seed.cjs` and `membership-seed.cjs`: prepare membership SQL from participant identities.
- `archive-evidence.cjs`: archive existing evidence through the verified storage implementation.
- `participant-accounts.cjs`: validate account and participant configuration.

Launchers resolve the repository relative to their own location; `HERBCHAIN_ROOT` can override it. `FABRIC_SAMPLES` can override the default `~/herbchain-fabric/fabric-samples` location. Do not run two API launchers against the same evidence directory.

## 6. Run the existing local pilot

Use Ubuntu/WSL for Fabric and the API. Install server and chaincode dependencies with `npm ci` in each package directory. Use Node 22 or newer for the launch scripts. Preserve the existing network volumes, enrolled identities and evidence directory.

1. Start the existing containers:

   ```bash
   docker start ca_org1 ca_org2 ca_orderer
   docker start orderer.example.com peer0.org1.example.com peer0.org2.example.com
   ```

2. Keep your existing private participant mapping, or copy `scripts/participant-accounts.example.json` to `scripts/participant-accounts.local.json` and fill in real Auth UUIDs. Example placeholders deliberately fail validation. Each participant needs the correct independently enrolled Fabric identity.
3. Keep the app's Supabase URL and public key in the untracked root `.env`. Server service credentials must never be Expo public variables.
4. From the repository root, start the API in its existing local mode:

   ```bash
   export HERBCHAIN_MEMBERSHIP_MODE=file
   export HERBCHAIN_BATCH_LIST_MODE=local
   export HERBCHAIN_EVIDENCE_MODE=local
   export HERBCHAIN_EVIDENCE_READ_MODE=local
   export HERBCHAIN_WRITE_MODE=local
   export HERBCHAIN_LOTS_ENABLED=false
   node scripts/start-farmer-api.cjs --accounts scripts/participant-accounts.local.json
   ```

   You can instead pass the absolute path to your existing account mapping. Keep this terminal open and visit `http://127.0.0.1:3002/dashboard`.

5. If a lock exists, inspect its recorded PID, running API processes and port 3002 first. Remove only a confirmed stale `.api.lock`; never remove the evidence directory to fix startup.
6. For Android, use the installed native development build. Expo Go cannot load this project's native TFLite dependencies. With USB debugging connected, reverse port 3002 and the actual Metro port, set `EXPO_PUBLIC_HERBCHAIN_API_URL` to `http://127.0.0.1:3002` for local USB testing, then run `npx expo start --dev-client --localhost` in Windows. A reachable HTTPS endpoint is needed outside this local development setup.

## 7. Validation and practical limits

Local automated coverage includes backend authorization and lifecycle rules, chaincode behavior, SQL policies/indexing/queue transitions, idempotency, private-evidence checks and failure recovery. Publication checks on 2 October 2026 passed 74 backend tests and 10 chaincode tests. The copied CommonJS launchers also passed syntax checks. Responsive browser checks previously used controlled fixtures; those checks are not proof of live performance or production readiness.

An earlier pilot recorded a complete 15-event demo chain through delivery, and an Android harvest was recorded on Fabric. The new database/indexer/worker modes and lot upgrade still require live end-to-end testing. The current publication task does not deploy those features or run a new Android native build.

## 9. Files intentionally kept private

Environment secrets, Fabric enrollment directories, Android signing keystores, real participant account mappings, generated membership seeds, harvest evidence, runtime identity files and build logs must remain outside the source publication. Git contains configuration examples, not a copy of the running ledger or Supabase database. The old repository already tracked the root `.env` (public Supabase configuration); untrack it with `git rm --cached -- .env` before committing. This preserves the local file and does not rewrite earlier Git history.
